WARN-2: postMessage handler trusts caller-supplied parentOrigin when event.origin is "null"
------------------------------------------------------------------------
Lines 6469–6475 (getTrustedParentOrigin function):

  function getTrustedParentOrigin(event) {
    const forwardedParentOrigin =
      typeof event.data.parentOrigin === "string" ? event.data.parentOrigin : null;
    const parentOrigin = event.origin === "null" ? forwardedParentOrigin : event.origin;
    return matchesAllowedOrigin(parentOrigin) ? parentOrigin : null;
  }

Context: When event.origin is "null" (opaque srcdoc iframe), the handler
accepts a caller-supplied event.data.parentOrigin string. The code comments
acknowledge this explicitly and explain the mitigation: replies are sent with
targetOrigin set to the claimed origin, so the browser drops the response if
the real top window doesn't match. The incoming message only triggers a DOM
screenshot capture (no auth, no data mutation), so the worst-case outcome of
a spoofed claim is that an attacker receives... nothing (the reply is dropped).

The allowedParentOrigins list also includes localhost entries:
  "http://localhost:3000", "http://127.0.0.1:3000",
  "http://localhost:5173", "http://127.0.0.1:5173"

These pose no risk in production (localhost is not reachable from the public
internet), but can be removed before launch to tighten the allowlist.

Action (optional): Remove localhost/127.0.0.1 entries from allowedParentOrigins
before final production deployment. The existing origin-check logic is sound.

Severity: WARN (design is intentional and mitigated; localhost entries are
cosmetic hardening)

WARN-3: No Content-Security-Policy (CSP) meta tag present
------------------------------------------------------------------------
The file does not include a <meta http-equiv="Content-Security-Policy"> tag or
any X-Frame-Options equivalent in the HTML.

Context: For a pure static site this is typically set at the web server / CDN
layer (Nginx, CloudFront, Vercel headers, etc.) rather than in the HTML. If
deployment infrastructure already sets security headers, this is not an issue.

Action: Confirm that the hosting layer sets at minimum:
  Content-Security-Policy: default-src 'self' https://maps.googleapis.com https://fonts.googleapis.com https://fonts.gstatic.com; script-src 'self' 'unsafe-inline' https://maps.googleapis.com; ...
  X-Frame-Options: SAMEORIGIN  (or use CSP frame-ancestors)
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer-when-downgrade

Severity: WARN (infrastructure gap, not a code defect)
